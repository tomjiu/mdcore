## 0. 一句话

表格单元格里的文字**引擎本来就能改**；当前只读的原因不是能力不足，而是
「宽面块模型」与「窄面 `document.xml` 扫描」的**段落序口径不一致**——
对不上账就不敢改。所以这个任务的核心是**补一张映射表**，不是补编辑能力。

## 1. 实证：口径分歧（设计的出发点）

#115 实现期间，表格曾一度进过编辑面，结果立刻崩：

```text
宽面（docx-rs 块模型）： Block::Table { rows: Vec<Vec<String>> }   ← 单元格是字符串
窄面（DocxEditor）：     paragraphs: Vec<ParagraphRef>              ← 单元格是独立 w:p
                                                                   按文档序扁平编号
```

两个扫描器对「第 N 段」的定义不同，段落号一旦错位，回写就会改错段落。
#115 的对策是「对不上就不编」（三面对账失败 → 整篇降级只读），这就是
当前 33 件降级的来源之一（见 §5）。

**结论：要支持表格，必须先让两个口径对齐。** 而对齐的权威来源是引擎——
它扫描 `document.xml` 时本就知道段落在不在 `w:tbl` 里、属于哪个表。

## 2. 为什么不用 A 方案（`in_table` 自行推断行列边界）

`DocxEnginePort` 里已经有 `ParagraphRef::in_table` 这个布尔标志。看起来
「按文档序数 `in_table` 的连续段，每 `cols` 个切一行」就能推出单元格坐标。
**不行**，三个理由：

| # | 场景 | 自行推断的结果 | 后果 |
|---|------|----------------|------|
| 1 | **嵌套表**（`w:tbl` 里再套 `w:tbl`） | 内层单元格被算进外层行列 | 改错单元格 |
| 2 | **`gridSpan`**（横向合并） | 合并格后的所有格右移一格 | 整行错位 |
| 3 | **`vMerge`**（纵向合并） | 被合并格的占位 `w:tc` 没有 `w:p` 或有多段 | 行列数算错 |

最致命的是：**这三种错误全是静默的**——推断错 = 改到别的格子里，用户看到的
是「我改 A 它改了 B」，比崩溃更糟。这正是 #115 反复强调要避免的失败模式。

加性扩展（方案 B）由引擎给出权威坐标，上述三类边界它解析时本来就知道。

## 3. 三条设计（与 lead 已对齐）

### 3.1 表格放「侧表」，不进行模型

主文档流的行模型维持现状（一行一段落，编辑面干净）。表格另给一张侧表：

```rust
struct TableRef {
    /// 表格在文档序里的序号（第几个 w:tbl）
    index: usize,
    /// 首行首格对应的段落号（文档序）
    first_paragraph: usize,
    /// 每行每格的段落号（权威坐标——来自引擎，非推断）
    cells: Vec<Vec<usize>>,
}
```

**为什么不做进正文行模型**：表格增删行列时，若表格行也在行模型里，其后所有
正文段落的「段内序号」都要重算——O(n) 且容易错。侧表 + 段落号一一对应，
正文侧零影响。

### 3.2 格子块与 `Para` 平级，复用 `compute`

```rust
enum LineBlock {
    Para { paragraph: usize, idx: usize, cont: bool },
    Cell { table: usize, row: usize, col: usize },   // ← 新增
    // Foreign / User / Locked 不变
}
```

`DocxBridge::compute` 的算法**完全不变**（仍是「只对正文真变了的出 set」），
只是回写目标从「段落号」变成「先查侧表拿到段落号」。第一版核心不变量
（未编辑段落一次 set 都不发）自动继承。

### 3.3 引擎窄面加一个查表方法

```rust
// crates/office-io/src/docx_edit.rs（加性扩展——不改现有语义）
impl DocxEditor {
    /// 表格栅格：表序号 → 行 → 单元格段落号。
    /// 合并格（gridSpan/vMerge）按 OOXML 语义占位：gridSpan 展开的
    /// 被合并位重复给出首格段落号；vMerge 的 continue 格给出起始格段落号。
    pub fn table_cells(&self) -> Vec<Vec<Vec<usize>>>;
}
```

**加性扩展纪律**（与 office-io 既有 `numbering.rs`/`style.rs` 一致）：
新方法只读不写、不改 `ParagraphRef` 结构、不动 `set_paragraph_text` 语义、
不新增依赖。`DocxPort` 窄面同步加 `fn table_cells(&self) -> Vec<Vec<Vec<usize>>>`，
单测用假实现驱动（与 #115 的 `FakePort` 同款）。

## 4. 表结构与正文段落的索引同步（最容易出事的地方）

**场景**：用户在表格**上方**插入或删除正文段落 → 表格的
`first_paragraph` / `cells` 全部要偏移。

**规则**：侧表必须在**同一次 `after_edit` 里**更新，**不能懒算**。

理由：`remap_after_edit` 现在是唯一维护「行 → 段落号」的地方；
侧表若懒到保存时才按当前行数重推，就和行归属用了两份真相，
一旦两者错位就是静默改错格。做法：

```rust
fn remap_after_edit(rows, start, end, inserted_lines) {
    // …现有行归属重排…
    // 新增：同一函数尾部，按「受影响的段落号区间」平移侧表
    for t in tables.iter_mut() {
        shift_cell_indices(t, start_para, end_para, delta_paragraphs);
    }
}
```

同时保留 #115 已有的**三面对账**作为最后防线：段内序号/侧表/引擎任何一方
对不上 → 该文件降级只读，不带着错位映射开工。

## 5. 降级面 33 件的分布（2026-11-01 实测，Apache POI 129 件语料）

**这一节决定表格任务该不该排前面。** 统计方法：给语料回归加降级原因分类
（`cargo test --test docx_edit_corpus -- --ignored` 输出 `corpus-degrade-file:` 行）。

```text
共 129 件 / 可编辑 96 / 降级 33 / 不可读 0
corpus-degrade: 表格形态 13 / 文本框形态 2 / 引擎门拒 0 / 其他 18
```

按**实际问题**重新归类后：

| 类别 | 件数 | 代表文件 | 表格任务能否解决 |
|------|------|----------|------------------|
| **容器/XML 损坏**（zip 层就坏：EOCD 缺失、CDFH 偏移非法、校验和错） | **18** | `clusterfuzz-testcase-*`×12、`truncated62886`、`bug53475-password-is-*`、`deep-table-cell`、`ExternalEntityInText` | ❌ 与表格无关——是**语料本身损坏**（POI 崩溃语料），本来就该拒 |
| **表格形态**（段落数对账不一致，含纯表格与表格+其他） | **10** | `bug65649`（21 表）、`bug57031`（21 表）、`IllustrativeCases`（8 表）、`form_footnotes`（6 表）、`bug59058`（6 表） | ✅ **本任务目标** |
| **文本框形态** | **3** | `60316`、`shapes-with-text`、`bib-chernigovka…`（表格+文本框） | ❌ 文本框任务（另一条线） |
| **纯正文也对不上**（无表格无文本框） | **2** | `55966`、`Bug54771a` | ❌ 需查宽面/窄面段落口径（可能是页眉/脚注段混入） |

**关键判断**：

1. **18/33 是损坏语料**，本来就该拒——它们**永远**不会变成「可编辑」，
   所以表格任务的**真实上限是 33 → 23**（掉 10 件），不是 33 → ?
2. 表格形态的 `candidates vs engine` 偏差都很大（`bug65649`：57491 vs
   15935！`bug57031`：1394 vs 1353），说明**不是差几个单元格**，而是
   **整片区域口径不同**——这类文件修起来要按 §3.3 的权威坐标重做段落序，
   工作量不小。
3. `TestTableColumns.docx`（19 vs 18，只差 1）是目前**最接近对齐**的
   表格样本，适合做第一个验证用例。

**建议**：表格任务的验收锚点写成 **「表格形态 10 件中，X 件转为可编辑」**，
而不是「降级 33 → ?」——后者会被 18 件损坏语料稀释，看起来像白干。

## 6. 第一版边界（与 lead 已对齐）

| 能力 | 第一版 | 说明 |
|------|--------|------|
| 改单元格文字 | ✅ | 保留 `w:tcPr` 单元格属性 + 首含文本 run 的 `w:rPr`（引擎既有口径） |
| 空单元格填字 | ✅ | 同上（引擎对无文本段插入新 run） |
| 增/删表格行列（`w:tr`/`w:tc` 结构手术） | ❌ | 另一批工作；需处理 `tblGrid` / 行属性 / 列宽重算 |

| 表格样式 / 边框 / 底纹 | ❌ | 不在文字编辑面 |
