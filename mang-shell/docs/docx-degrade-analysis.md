# docx 降级面分析：32 件为什么不可编辑

> 状态：**实测结论**（2026-11-01，Apache POI 129 件语料）。
> 本文回答一个问题：**降级面里到底有多少是「表格问题」、多少是架构边界。**
> 结论：**大部分不是表格问题**，表格任务已做到它的上限附近。

## 0. 一句话

129 件语料里 97 件可编辑、32 件降级。其中：
- **18 件是损坏语料**（zip 层就坏）——本来就该拒，永远不可编辑；
- **14 件是宽面/引擎段落计数不一致**——细分为四类，**只有约 2 件是纯表格问题**。

## 1. 当前基线（实测）

```text
共 129 件 / 可编辑 97 / 降级 32 / 不可读 0
corpus-degrade: 表格形态 12 / 文本框形态 2 / 引擎门拒 0 / 其他 18
```

> 表格编辑任务（#126 + #128）把可编辑从 96 提到 97、降级从 33 降到 32。
> 唯一转正的是 `TestTableColumns.docx`。

### 1.1 TestTableColumns 为什么「只差 1」

这是本次最重要的口径澄清：

```text
宽面 TableData::rows = 栅格展开形
  gridSpan 覆盖列重复补列 / vMerge 续格也补列
引擎 = 一个 w:tc 一个段落

TestTableColumns 第 2 张表末行：3 个 tc，第 3 个带 gridSpan=2
  → 宽面算 4 格、引擎只有 3 个 w:p → 正好差 1
```

**不是「少了个格子」，是两种坐标系的差异。** 修复 = 对账时用引擎
`DocxEditor::table_cells()` 的权威栅格，而不是宽面展开格数。

## 2. 14 件不匹配的四类归因（实测数据）

方法：逐件比对「宽面文档序段落数」与「引擎 `w:p` 数」，并统计
`w:sdt` / `w:tbl` 内 `w:p` / 嵌套表深度等结构特征。

```text
文件              宽面    引擎    差     类别
55966               2       3     1   D 接近
60316               9      32    23   A sdt
60329              34      32    -2   C 嵌套表（宽面反而多算）
Bug54771a           0      10    10   （见 §2.5）
Bug54849           20      43    23   A sdt
Bug55142           11      19     8   A sdt
IllustrativeCases 127     388   261   B 一格多段
bib-chernigovka   568     569     1   D 接近
bug57031         1349    1353     4   D 接近
bug59058          855     953    98   B 一格多段
bug65649        12236   15935  3699   B 一格多段
drawing           213     227    14   C 嵌套表
form_footnotes     89     215   126   B 一格多段
shapes-with-text    5      11     6   （文本框形态）
```

### 2.1 A 类：`w:sdt` 结构没被宽面提取（3 件）

```text
Bug54849   deficit=23  sdt=9   p_in_sdt=21
Bug55142   deficit=8   sdt=8   p_in_sdt=8
60316      deficit=23  sdt=27  p_in_sdt=27
```

deficit ≈ `p_in_sdt`，**完全解释**。宽面块模型不把 `w:sdt`（内容控件）
里的段落提到块流里。

### 2.2 B 类：单元格里有多个 `w:p`（4 件）——最主要

```text
IllustrativeCases  tc=48    p_in_table=309   deficit=261
form_footnotes     tc=77    p_in_table=203   deficit=126
bug59058           tc=595   p_in_table=693   deficit=98
bug65649           tc=13367 p_in_table=15204 deficit=3699
```

**这里是关键澄清**：以 IllustrativeCases 为例，

```text
实际 w:p = 388，其中 309 个在 w:tbl 里，只有 79 个在表外
宽面算出 127 = 79（表外正文）+ 48（tc 数）
引擎算出 388 = 79 + 309
```

所以**不是「宽面丢段」，是「宽面把一格当一个段落」**：

```rust
// 宽面（docx-rs 块模型）——文本读面
pub struct TableData {
    pub rows: Vec<Vec<String>>,   // 一格 = 一个字符串
}

// 引擎（document.xml 扫描）——结构读面
// 一格 = 若干 w:p（文档序扁平编号）
```

`bug65649` 平均每格 1.14 段——说明**真实标书里「一格多段」是常态**，
不是异常数据。

### 2.3 C 类：嵌套表被宽面平铺成独立表块（2 件）

```text
drawing    maxdepth=4  nested_tbl=7  deficit=14
60329      maxdepth=2  nested_tbl=4  deficit=-2（宽面反而多算）
```

宽面把内层 `w:tbl` 递归提取成**独立的表块**（`nested: true`），
而不是留在外层单元格里；引擎按文档序扁平计数。两种口径不同。
`60329` 的 deficit 是负数 = 宽面重复计数。

### 2.4 D 类：已基本对齐（3 件）

```text
bug57031           deficit=4 (0.3%)
bib-chernigovka    deficit=1 (0.2%)
55966              deficit=1
```

差个位数，可能是个别空段落/边缘段落。**优先级低。**

### 2.5 特殊：Bug54771a（宽面 0 / 引擎 10）

宽面一个块都没读出来，引擎有 10 个 `w:p`。属于宽面解析的特例，
需单独排查（不在本次分析范围）。

## 3. 结论：不是 bug，是架构边界

```text
宽面 = 文本投影（一格一个字符串）
引擎 = 结构读面（一格若干段落）

这两者【本来就是不同层次的东西】，不一致是设计使然，不是缺陷。
```

**因此不单开「查宽面丢段」的任务**——没有 bug 可查。

## 4. 如果要继续（方案 2：表格段落序以引擎栅格为准）

技术上可行的雏形已经有：`DocxEditor::table_cells()`（#126）。

### 4.1 技术路径

```text
push_table 不再用 t.rows 的格数当段落数
而是逐格展开引擎栅格里的段（一格可能有 1..n 个 w:p）
对账口径改成「引擎栅格覆盖的段落号集合」
```

预估能再解掉 A/B 两类共 **4-6 件**（降到 26-28 件降级）。

### 4.2 前置依赖（UI 必须先定）

**「一个 tc 里的第 2..n 段怎么在行模型里表示？」** 这是最大风险：

```text
如果每段一行 → 用户看到「一个格子占好几行」，视觉上散架
如果只显示第一段 → 其余段的内容用户看不到（静默丢失）
```

候选方案（需 docx-ui 那条线决定）：

| 方案 | 显示 | 编辑 | 风险 |
|------|------|------|------|
| 格内 `¶` 分隔 | 一格一行，段间 `¶` | 按 `¶` 编辑，回写拆成多 `w:p` | 中（`¶` 与正文冲突） |
| 只显示首段 | 一格一行 | 只能改第一段，其余标 `Locked` | 低（但用户看不到内容） |
| 一格多行 | 一格占多行 | 逐段可编辑 | 高（行模型与表格栅格解耦变复杂） |

### 4.3 为什么现在不做

1. 剩下能解的只有 4-6 件；
2. 需要 UI 侧先设计「一格多段怎么显示」；
3. 这 4-6 件是**测试语料**，不是用户的真实需求；
4. 97/129 可编辑已覆盖绝大多数真实文档。

## 5. 给后来人的话

如果你看到「32 件降级」想修：

1. **先看这 32 件的构成**——18 件是损坏语料（zip 坏），修不了也不该修；
2. **剩下 14 件里只有约 2 件是纯表格问题**（`bug57031`、`bib-chernigovka` 那类差个位数的）；
3. **最大的那批（B 类）不是丢段，是「一格多段」**——修它需要先解决 UI 表达。

**别一上来就看 `bug65649` 的 4 万段差距**——那是个大表文档，
13367 个单元格包着 15204 个段落，差距来自「一格多段」，不是 bug。
