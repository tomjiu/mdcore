## 侦察实证（写代码前完成的钉定与探针）

**ABI 钉定**：LibreOffice/core `0d51fdc57aef6707466320821b8c2931c00297c0`
四个头文件（LibreOfficeKit / Init / Enums / Types）下载留档审查。关键事实：

- vtable 首成员 `size_t nSize` + append-only 槽位 → 运行时成员检查
  依据（本实现严于 C 宏：`offset + 8 <= nSize`）；
- `hook_2(install_path, user_profile_url)`：**install_path = program
  目录**（init.cxx:8208 `BRAND_BASE_DIR = aAppURL + "/.."`；Init.h 的
  注释说安装根目录是**误导**——两次实测翻车后以源码+C 探针收口）；
- profile 支持 `vnd.sun.star.pathname:<系统路径>`（init.cxx:8196）；
- `saveAs` 返回**布尔语义非 0=成功**（`return true`→1；探针实证
  rc=1 时产物有效落盘——首轮按 POSIX 0=成功 解读把成功误判为失败，
  以 /tmp 实际产物反证纠正）；
- Enums 头（该 commit 已从 Types.h 拆出）：回调号 INVALIDATE_TILES=0 /
  STATE_CHANGED=8 / UNO_COMMAND_RESULT=16；键鼠事件 0/1/2；TILEMODE
  RGBA=0/BGRA=1。

**C 探针先行**（gcc 直编 dlopen，先于任何 Rust 投入）：Debian
LibreOffice **25.2.3.2** 的 hook 在 `program/libmergedlo.so`（`nm -D`
实证；`libuno_sal.so.3` 无），探针全链 PASS：hook_2 → getVersionInfo
→ documentLoad（Writer type=0）→ getDocumentSize 12474×17406 →
paintTile 400×300 tileMode=1 非白像素 19768（红蓝图片均现形）。
运行时 nSize：kit=208（钉定头 26 槽全量 216 → 尾槽缺席，nSize 守卫
必要性的活例）、doc=640。

**参考审查**：ElyOffice ely-lok/ely-ipc（MIT，commit dc32744d）——
借协议/进程模型/环境变量/Windows 加载模式/unipoll 集成，不整包搬运。

## 实现（crates/lok = mdc-lok，纯引擎面）

- `ffi.rs`：钉定头 vtable 全槽位声明 + nSize 守卫 + 加载序
  （sofficeapp>1000B 否则 merged；Windows `LoadLibraryExW` 搜索标志
  同目录解析依赖）+ `freeError` 跨 CRT 释放纪律 + 路径→file: URL
  （盘符冒号不编码，重写时新增单测抓到并修复该 bug）+ `runLoop`；
- `proto.rs`：24B 头帧（magic/kind/id/长度上限：JSON 1MiB、bin 64MiB），
  超限**分配前**拒绝；UNASKED=0 事件推送；tile 像素二进制直传；
- `worker.rs` + `src/bin/mdc_lok_worker.rs`：单文档 worker 进程。
  **unipoll 主循环集成**（runLoop + poll 回调消费请求 = 主循环上下文
  同步分发）；fd 0 抢救（dup + NUL，防 LO 内嵌组件抢读协议流）；
  保存目标≠加载源硬守卫；退出 `_exit`（绕开 LO atexit 崩溃面）；
- `backend.rs`/`mock.rs`：DocSession trait，真实/mock 同构（mock 可
  注入挂起/保存失败，save 写真实 zip 供 CI 校验保存链）；
- `client.rs`：spawn（独立 profile + TMPDIR 重定向 + unipoll env）/
  请求 ID 关联（**先登记后写**，见下竞态修复）/超时/EOF 崩溃检测
  （stderr 尾部随错）/kill+重拉；
- `session.rs`：脏位语义（超时/死亡/保存失败一律不清）+ 保存安全链
  （临时产物→结构校验→决定替换才清）+ 相对路径规范化 +
  wait_for_event（事件暂存不丢）；
- `verify.rs`：原型级最小 zip 读取器（EOCD/CD/LFH；stored+deflate）；
- `examples/smoke.rs`：全链诊断（runtime/tile PNG×3/保存回执/摘要
  前后对比）；产物归档 `crates/lok/diagnostics/`。

依赖卫生：libloading 0.9 / flate2 1.1.10 取 Cargo.lock 现解析直依赖
（零新编译单元，循 mdc-pdf sha2 先例）；PNG 复用 `mdc_canvas::encode_png`
（dev-dep，不引 png/image）。

## 两大实战 bug 记录（先红后绿）

### 1. 异步事件黑洞（真实模式编辑静默丢失）

**症状**：smoke 首跑全绿后，连续复跑两种失败形态——①键入中途
`post_key` 15s 超时（worker 活着）；②事件到达但编辑后 tile 像素
不变；saveAs 产物里**没有**键入的文本（编辑根本没进文档模型）。

**诊断链**（全部实测取证）：
- /proc 线程转储：`lo_startmain` 线程 wchan=futex_wait_queue_me 整段
  沉睡；6s 纯等待无效（CPU 仅 0.05s/6s，非忙轮询）；
- saveAs 触发后积压的键入事件**迟到涌出**（排队事件被延迟消费）；
- 同期 C 探针（单线程直连）键入正常 → 差异在多线程宿主架构；
- 读钉定源码收口：Writer 的 `postKeyEvent/postMouseEvent` 均为
  `postKeyEventAsync` → `Application::PostUserEvent` 入队（unotxdoc.cxx
  :4015-4018）；消费依赖 `lo_startmain` 线程跑主循环；svp 后端的
  `ImplYield` 在无定时器且无唤醒时无限等（svpinst.cxx）。外部宿主
  场景下该线程可永久沉睡 → 排队事件黑洞。

**修复**：真实模式强制 `SAL_LOK_OPTIONS=unipoll`（env 在 hook_2 前
生效）+ worker 分发线程进入 `runLoop`（poll 回调里消费请求通道 =
主循环上下文同步分发；wake 回调经共享通道叫醒 poll）。unipoll 下
`postEventAsync` 直调 `LOKPostAsyncEvent`（lokhelper.cxx:1283-1290），
同步确定。ElyOffice Linux 同款模型（worker/unipoll.rs）。

**验证**：修复后 smoke 连跑 3/3 全绿（此前 4 连败）；lok_real 真实
门 0.55s 通过（此前不可测）。中途一次教训：只设 env 不进 runLoop
会 SIGSEGV（rc=-11）——unipoll 改变了初始化路径，必须配套 runLoop。

### 2. 宿主 pending 登记竞态（假超时）

**症状**：boundary 套件间歇性 1 例失败（8 轮内 2 次），`post_key
(#7) RequestTimeout 15000ms`——mock worker 毫秒级响应却超时。

**根因**：`call()` 先写请求、后登记 pending 通道；mock 响应微秒级
返回，读线程在 pending 里找不到 id → 响应被丢弃 → 调用方等到超时。
并行测试负载下主线程在两步之间被调度出去即触发。

**修复**：先登记后写（写失败则移除登记）。**验证**：修复后 boundary
连跑 10/10 全绿（修复前 ~25% 失败率）。
