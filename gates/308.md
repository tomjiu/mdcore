# #308：签名摘要验证——验签第②层 digest_matches（2026-11-07，P1 / 研究仓 acrobat-mapping §6）

**背景**：验签三层模型（① 结构完整 ← 已有；② 摘要一致 ← 本条补；
③ 信任链 ← 需要信任根明确不做）。修复前 signature.rs 只验结构：
`structurally_valid` 不表示签名有效、ByteRange 只收集不校验、
「签的是这些字节吗」无答案——用户最关心的「这份合同签了之后有
没有被改过」答不了。这是与 Acrobat 验签的最小差距（Acrobat 至少
做摘要一致性）。

**先核实**：缺口在 HEAD 仍在（CmsSummary 无 messageDigest 提取、
build_signature_info 无字节摘要比对）。**方法预验证**：开工前用
Python 独立复算——夹具 ByteRange [0,14228,18720,608] 两段 SHA-256
与 CMS signedAttrs 的 messageDigest（8deac48d…）完全匹配，路走得
通后才写 Rust。

**实现**（分支 `feat/308-digest-verification`，基于 main `7178eba`）：

- **依赖**：`sha2 = 0.11`（**锁内既有**——mdcore chunk_id 同版本在用，
  Cargo.lock 净增 1 行依赖边，零新增 crate），optional 随
  `engine-lopdf` 门（signature.rs 同门，默认构建零依赖纪律保持）；
- **CMS 面补解析**（parse_signed_data）：
  - SignerInfo **自身** digestAlgorithm 捕获（messageDigest 的算法
    权威在 SignerInfo，非外层 digestAlgorithms SET——标准只约束前者）；
  - `signedAttrs [0]` 提取 messageDigest（OID 1.2.840.113549.1.9.4
    的 OCTET STRING 原始字节）——新 `find_message_digest`（宽容读面：
    多属性按 OID 精确定位，找不到 → None 不猜）；
- **验证面**（新 `verify_digest`）：
  - ByteRange 区间合法性前置（偶数个/非空/不越界/不重叠——重叠即
    无法确定覆盖面，宁不验证）；
  - 各段按序喂 SHA-256/384/512 → 与签时基线逐位比对；
  - 三类诚实 None：算法不支持（sha1/md5 等旧算法）/ 基线缺失
    （无 signedAttrs）/ 区间非法；
- **载荷面**：`SignatureInfo` 新增 `digest_matches: Option<bool>` +
  `digest_issue: Option<String>`（与 structurally_valid/
  structural_issue 同款「判定 + 原因」模式；`#[serde(default)]`
  wire 向后兼容——旧 JSON 反序列化 → None 默认，测试锁死）；
  `build_signature_info` 接收原始文件字节（摘要对 ByteRange 覆盖的
  **原字节**算，不是重解析产物）；
- **文档**：模块头新增「验签三层」节——**digest_matches = Some(true)
  不等于证书可信**（自签证书也过这关；也不验签名数学有效性——那
  需要内嵌证书公钥做非对称验算 + 信任链判定，属第③层）。

**诚实边界**：

- sha1/md5 摘要不支持（sha2 面只有 256/384/512）→ None + 原因。
  旧算法签名在野存量不小，后续可评估加 `sha1` crate（需 Lead 裁定
  ——那是**新增 crate**，与「锁内既有零新增」纪律不同级）；
- 不验签名数学有效性（第③层的邻接半步：用内嵌证书公钥验 RSA/
  ECDSA 不需要信任根，但需要非对称实现——本条按 issue 范围止步于
  摘要比对，数学验签登记为后续）；
- 夹具为自签证书（pyhanko 生成）——对第②层无影响（摘要一致性与
  证书信任无关），已在测试文件头登记。
