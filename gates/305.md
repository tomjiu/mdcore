# #305：渲染缓存标注失效——键控（RenderKey + annotation_rev）与显式失效双轨（2026-11-07，P1 / 研究仓 acrobat-mapping §10.6）

**背景**：`render_annotations(true)` 渲染面下缓存位图含标注
（engine_pdfium.rs 显式钉定）；flush 落盘新标注后缓存即陈旧，而 crate
无任何「标注变更 → 缓存失效」API。用户面后果（issue 原话）：加标注
→ 保存 → 屏幕还是旧位图 → 用户以为「加标注没生效」。审计 P3 维持，
排期定位「接 UI 前置」（#302 的前置件之一）。

**先核实（未盲目动手）**：研究仓基线 mdcore@6322f86（2026-11-04）早于
#227 修复链——但本条与 #303 不同，**缺口在 HEAD 仍在**：cache.rs 键为
纯泛型 (页, 宽) 无 rev 概念；PdfSession flush 无产物身份面；渲染缓存
零失效 API。核实结论与修复同时交付。

**实现**（分支 `fix/305-cache-invalidation`，基于 main `7178eba`；
issue 倾向「方案 A + B 都提供」，照做）：

- **方案 A 键控**（自动失效——旧键自然 miss）：
  - `render.rs` 新增 [`RenderKey`]（page/width_px/height_px/
    annotation_rev 四因子，`Copy + Eq + Hash` + serde 同
    RenderRequest 家族）；语义合同：**key 相等 ⟺ 光栅输出可复用**；
    构造面 `new` + `from_outcome`（请求页 + 产物尺寸 + 会话 rev——
    渲染回执落账最短路径）；
  - rev 源头双面（同款合同，`saturating_add(1)`）：
    [`PdfSession::annotation_rev`]（flush 成功且 `bytes_appended > 0`
    时 +1；两路径统一走 `bump_rev_if_appended`——零脏短路路径与
    脏集路径同纪律）与 [`PdfAnnotator::annotation_rev`]（save 成功且
    追加 > 0 时 +1）。**零追加幂等 flush/save 不 bump**（位图没变——
    命中率不因空转全体 miss）；失败 flush 不 bump（产物未变）；
  - `lib.rs` 导出 `RenderKey`（常开面）。
- **方案 B 显式失效**（预算即刻回收——键控只让旧键不被取用，条目
  仍占预算直到 LRU 驱逐）：
  - `cache.rs` 泛型面：`invalidate(&K) -> Option<V>`（单键精准摘除，
    返回值 = 调用方作废关联资源的载荷；幂等）+
    `invalidate_matching(pred) -> Vec<K>`（谓词批量摘除，返回键集
    **LRU→MRU 序**——与 `put` 驱逐键集同款载荷面）。内部原语
    `remove_slot`（摘链 + map 移除 + 退成本 + 槽入空闲栈）；
    `evict_tail` 既有行为零改动；
  - `render.rs` PDF 感知粒度（`impl<V> PageCache<RenderKey, V>`）：
    `invalidate_page`（页级影响域）/ `invalidate_stale_revisions`
    （`rev < current`——flush 后旧位图即刻回收，当前 rev 条目零扰动）/
    `invalidate_all`（全量，返回键集版；与 `clear` 按「要不要键集」
    分工）。

**测试证据**（本机 Linux 实测，rustc 1.99.0 工具链钉住版）：

- 新语义锁文件 `tests/pdfo_render_cache_rev.rs` **11 条**（常开：零
  引擎依赖零语料依赖，CI Windows 可全量运行；第 11 条 feature
  `engine-lopdf` 门内走真写器 + 仓内 fixture small.pdf）：
  1. `flush_bumps_rev_only_when_bytes_appended`——零脏幂等 flush 不
     bump / 有脏 flush +1 / 单调递增（MockWriter 确定性追加模型）；
  2. `flush_failure_keeps_rev`——TapWriter 注入失败：失败不 bump，
     重试成功才 bump；
  3. `stale_rev_key_misses_after_flush`——验收 4 主锁：flush 后新键
     miss（重渲染根机制）+ 旧键仍在位（键控 = 不服役不销毁）；
  4. `re_render_after_flush_refills_and_hits`——端到端 mock 光栅化器
     计数：3 页初渲染 3 次 → 同 rev 稳态零 rasterize → flush +
     invalidate_stale_revisions（恰回收 3 条旧 rev）→ 重渲染恰 3 次
     （**不多不少**）→ 新稳态零 rasterize。验收 1/2/3 的 mock 化；
  5. `invalidate_stale_keeps_current_rev_entries`——混合 rev 共存下
     只摘旧的（跨 rev 回看场景命中保持 + bytes 精确回收）；
  6. `invalidate_page_is_scoped`——页级粒度（含同页异宽度条目）；
  7. `invalidate_all_returns_keys_lru_to_mru`——返回序含提权后顺序；
  8. `render_key_discriminates_all_factors`——四因子判别完备性 +
     from_outcome 合成；
  9-10. 泛型面：invalidate 返回值/幂等/预算回收；
     invalidate_matching 序与预算；
  11. `annotator_rev_matches_session_contract`——PdfAnnotator rev 与
      会话同款合同（真写器追加 > 0）。

**验收对照**（issue 四条）：

| 要求 | 证据 |
|---|---|
| 1. 加标注 → 重渲染 → 位图包含新标注 | 锁 3/4：rev 入键使 flush 后新键 miss → 触发重渲染（真 UI 接线 = #302 消费本 API；沙箱无 pdfium，引擎面以 mock 锚定，诚实边界如下） |
| 2. flush 后渲染不再是旧位图 | 锁 3/4：旧键不被新键取用 + invalidate_stale_revisions 即刻回收（占预算问题一并收口） |
| 3. 缓存命中率不明显下降 | 锁 1（零追加 flush 不 bump）+ 锁 4（同 rev 稳态零 rasterize）+ 锁 5（跨 rev 共存命中保持） |
| 4. 单测：模拟改动 annotation_rev，断言缓存 miss | 锁 3 `stale_rev_key_misses_after_flush`（正是该场景） |

**诚实边界**：

- 本沙箱无 libpdfium——引擎面（engine_pdfium rasterize 真渲染）
  未实机验证；但本条改动**不触引擎代码**（渲染面既有行为零变化，
  改的是缓存键与失效 API），mock 锚定即语义面全集；
- mang-shell `PdfPagesView` 的键从 (页, 宽) 迁到 RenderKey **不在本
  PR**：该视图当前无标注写路径（#302 实证 mang-shell 标注零接线），
  迁键 = 为不存在的 flush 路径接 rev（恒 0），纯抖动；#302 接标注
  UI 时按 `RenderKey::from_outcome(request, rendered, session.
  annotation_rev())` 落账即得完整失效链（PR 描述附迁移指引）；
- pdfium feature 面（`engine-pdfium`）未跑（沙箱无库）——CI
  windows-test 跑 `--features engine-lopdf,engine-pdfium`，本条新测试
  面纯 Rust 零外部依赖，Windows 可全量运行。

**CI 面**：windows-check（cargo check 双目标）/ windows-test
（mdc-pdf features 全开）均覆盖；无新外部依赖（serde 既有）。
